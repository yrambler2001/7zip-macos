# `fix111`: user-reported bugs for 7-Zip 26.04 for macOS 1.1.1

Branch `mac/fix111`, off `macos` at `6d09e43` (1.1.0), 2026-10-07. Four bugs reported from real use
of 1.0.0, plus the problems of the same kind found while fixing them.

## 1. "E_FAIL Unspecified error" on an app bundle

**Reproduced** with the user's own `~/Applications/Chrome Apps.localized/` (a Chrome web-app shim:
`Contents/{Info.plist, PkgInfo, MacOS/app_mode_loader, Resources (0700), _CodeSignature}`, Finder
info and quarantine attributes, an `Icon\r` file with a resource fork, a `.localized` folder) and
with copies of `/System/Applications/Calculator.app`.

**Root cause.** The bridge listed every one of these folders correctly. The failure was in
`PanelViewController.openRow`: a directory that `NSURLIsPackageKey` calls a package was treated as
a file and handed to `SZArchiveOpener.openArchive(in:itemIndex:)`, which opened the directory as an
archive stream. The engine answered `E_FAIL`, not `S_FALSE`, so the panel showed the error box
instead of falling back.

**Fix.**

- Enter (and a double-click) on any directory binds it, as 7zFM does (`IsItem_Folder` →
  `OpenFolder`, PanelItems.cpp:1090-1091). 7zFM has no packages. Open Outside (Shift+Return) still
  hands an app to Launch Services.
- `openArchiveInFolder:` answers `SZErrorCodeNotArchive` for a directory item, as
  `openArchiveAtPath:` already did, so no caller can get the `E_FAIL` again.

**Per-item problems.** Checked that none fails the folder: broken and looping symlinks, a link to a
folder, an unreadable folder and file (`chmod 000`), a FIFO, resource forks, Finder info,
quarantine, `Icon\r`, names with LF, TAB and BEL, a `.localized` folder, and an app bundle. Every
property of every item reads. Entering the unreadable folder is an error of that folder only (the
same on Windows), and flat view walks past it.

## 2. A row's text drawn higher than the others

**Root cause.** The name cell centred its `NSTextField` vertically. A field is as high as the text
it holds, and the CR of `Icon\r` made a second (empty) line. The field doubled in height and its
first line moved up by half a line. A name whose glyphs come from a taller fallback font (emoji,
Tibetan stacks, stacked combining marks) moved the same way by a smaller amount.

**What 7zFM does.** `SetItemText` (PanelListNotify.cpp:384-438) passes the name to the list as it
is, apart from RLO → `_` and runs of spaces, and the list control draws it on one line, where a
control character draws nothing. Other text columns replace LF and CR with spaces
(PanelListNotify.cpp:470-479). An empty display name becomes `_`.

**Fix.**

- Every list cell pins the text field's first baseline at `PanelMetrics.textBaseline(for:)`: the
  baseline a one-line field of the list font has when centred in the 19 pt row. That is the place
  every row had before, so ordinary rows do not move.
- `usesSingleLineMode` is set on the cells.
- `Formatting.displayName` drops C0 controls, DEL, NEL and U+2028/U+2029, and shows `_` for a name
  made only of them. `Formatting.cellText` shows LF and CR as spaces. The name itself (rename, copy,
  sort, the item's path) is unchanged.

## 3. Sorting from the column headers

**Mac before.** A click on a header already sorted, and a second click reversed the order
(`PanelTests.testSortBySizeStartsDescendingAndKeepsFoldersFirst` clicks it with the real mouse).
Size and the three times start descending, Ctrl+F3…F7 (Cmd here) and View > Arrange By worked, and
the sort was saved per folder type. There was no arrow in the header.

**7zFM 26.04 source.**

- Nothing in `CPP/7zip/UI/FileManager` (or anywhere in `CPP/`, `C/`) sets `HDF_SORTUP`,
  `HDF_SORTDOWN`, `HDM_SETITEM` or `LVM_SETSELECTEDCOLUMN`.
- `OnColumnClick` only calls `SortItemsWithPropID` (PanelSort.cpp:256-286).
- The list control draws a header arrow only when it is asked to.

listfeel's capture of 26.03 showed a plain "Name" header.

**Windows re-check.** The reference PC did not answer during this pass (`ssh` timed out for the
whole session), so 7zFM 26.0x could not be captured again. The capture script is ready (header
`fmt` flags and rects through `HDM_GETITEM`, real header clicks, Ctrl+F3…F7, the View menu's check
marks, restart and archive-type persistence, the status bar's part rects and borders, and the
`Icon\r` / LF / TAB names inside a tar). It should be run before the header arrow question is
closed for good.

**Decision.** No arrow, as the source draws none.

**Fix.** One real difference was found: `GetSortControlID` (MyLoadMenu.cpp:82-95) checks Name in
View > Arrange By when the sort column has no menu item of its own (Created, Packed Size, …). The
port checked nothing; it now checks Name.

**Tests.** `Fix111Tests.testHeaderClickSortsReversesAndPersistsPerFolderType` covers the click
order, the reversal, the descending-first columns, the menu checks, no indicator, the archive
type's own sort, and a new window reading the saved sort.

## 4. Status-bar margins

**Windows.** Measured on the fresh-default 26.03 captures (96 dpi, `PrintWindow`):

- The status bar is `msctls_statusbar32`, 23 px high, with parts ending at 220 / 320 / 420 / −1.
- Part 0's ink ("0 / 15 object(s) selected") starts at client x **2**.
- Parts 1-3 start their ink 2 px after the part's edge (recheck §2), and the dividers are at
  part edge − 1.
- The client area is 1 px inside the window's visible border, and Windows 11 rounds the corner by
  8 px. At the text's lowest ink that costs about 1 px, so the text clears the frame.

**Mac.**

- The same 2 px from the panel's edge (ink at 1.5 pt).
- A macOS window has no border, and its bottom corners are rounded by **16 pt on macOS 26** (10 pt
  before; read from the window on 26.6). At the text's lowest ink (3 pt above the window's bottom)
  that corner reaches 6.7 pt in, so the first digit was cut by the frame.

**Fix.**

- The panel whose status bar starts at the window's left edge moves part 0's text in by the 1 px
  border plus the corner's reach at the text's lowest ink: `PanelMetrics.statusCornerInset`, 8 pt
  on macOS 26 and 4 pt before. It is not applied in full screen, where the corners are square.
- Parts 1-3, and part 0 of the right-hand panel, keep Windows' 2 px.
- The right side needs nothing: the parts' text is left-aligned and cut at the part's edge − 2, as
  before.

**Test.** `Fix111Tests.testStatusBarTextInsets` measures the ink of all four parts in both panels.

## 5. Other problems of the same kind

| problem | status |
|---|---|
| **Names outside the BMP showed as empty rows** (emoji, flags, `𝄞`), in folders and inside archives. The engine keeps UTF-16 surrogate pairs in its 32-bit `wchar_t` ("We store 16-bit surrogates even in 32-bit WCHARs", UTFConvert.h), and `SZStringFromWChars` decoded them as UTF-32, which rejects surrogates: the whole name became "". | **fixed**: each unit below 0x10000 is taken as a UTF-16 unit, a real UTF-32 point is split into its pair. `Fix111BridgeTests` covers file-system folders and 7z, zip and tar archives. |
| View > Arrange By with a sort column that has no item | **fixed** (§3) |
| Other text columns (comment, link target) with a line break | **fixed** (§2) |
| A path with a control character in the address bar or the window title | left: shown as is (7zFM does the same in its edit control) |
| `ThemeTests.testMainWindowIsReadableInBothForcedThemes` failed once in a full `-H` run (every text measured white on white), and passed alone and in the next full run | flaky, not caused by this branch; noted |
