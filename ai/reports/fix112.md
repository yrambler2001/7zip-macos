# `fix112`: 7-Zip 26.04 for macOS 1.1.2

Branch `mac/fix112`, off `macos` at `ca600ff` (1.1.1), 2026-10-07. One user-reported bug, two
user decisions, a Homebrew change.

## 1. A header click did not sort with the user's saved settings

**Report.** On a MacBook that had run older builds, clicking a column header did nothing; a fresh
settings domain (`SEVENZIP_DEFAULTS_SUITE=sorttest`) sorted.

**The user's values** (column and sort values only; no path from their dump is in the repository):
`FM.Columns.FSFolder` sorted by Created (propID 10) ascending, Name 464 wide, many hidden columns;
archive layouts sorted by Packed Size / Size descending; `FM.ListMode0/1 = 3` (Details),
`FM.Panels.numPanels = 1`, **`FM.ShowDots = 1`**, `FM.Theme = light`.

**Root cause: `FM.ShowDots = 1`** (Options ▸ Settings ▸ Show ".." item). Not the column layout.
`PanelViewController.sort(by:toggle:)` sorts a folder that implements `IFolderCompare` on the panel
queue and guarded that path with `folder.itemCount >= unsorted.count`. With Show ".." the rows hold
one more entry than the folder has items (the `..` row, `engineIndex -1`), the guard failed by one,
and the closure returned without a word. The sort ID was already saved and View ▸ Arrange By
followed it, but the rows never moved. `CFSFolder` implements `IFolderCompare` (FSFolder.h:83), as
does every archive folder, so this hit every folder except the root list; the fresh domain has
ShowDots off, which is why it worked there. The same guard also dropped the IFolderCompare pass that
follows a load. Reproduced in the host before the fix (`Fix112Tests`: "Name ascending" stayed in
Created order) and passing after it.

**Fix.** The guard checks only engine rows (`PanelSorting.engineIndicesAreValid`), and when the
folder has changed under the rows it still sorts them from the snapshot's values instead of
dropping the click.

**Sanitising stored layouts** (nothing stored may block sorting):

- `Settings.ColumnLayout` decodes leniently: a missing `sortID` / `ascending` / `visible` / `width`
  gets its default, numbers stored as strings or booleans as numbers are read, a column entry that
  does not decode is skipped instead of losing the whole layout, a layout stored as `Data` loads.
- `PanelColumnsModel` already dropped unknown and duplicate column IDs, kept Name first and visible,
  and ignored a sort on a column the folder does not have; widths are now clamped to 24...4000.
- A sort on a hidden column is kept (7zFM allows it through Ctrl+F3...F7), and a click still changes it.
- The panel sets no `autosaveName`, so `NSTableView Columns ...` / `Sort Ordering` keys are never read.

**Tests.** `Fix112LayoutTests` (unit): the user's layout, the ".." row and the item count, messy
layouts (duplicates, unknown and negative IDs, no Name, absurd widths, wrong types, a sort on an
absent / hidden column, not JSON). `Fix112Tests` (app-hosted): the user's FSFolder, RootFolder and
zip layouts with ShowDots on, header clicks in a folder and inside a zip; seven corrupt values of
`FM.Columns.FSFolder` with legacy NSTableView keys present, each sorting by Name and Size from the
header. `Fix112UITests.testHeaderClicksSortWithShowDotsAndAStoredLayout` (real clicks).

Not done: building v1.0.0 / v1.1.0 to generate old settings. The user's real values arrived first
and reproduced the bug directly, so the scratch worktrees were removed unbuilt.

## 2. Options ▸ macOS ▸ Reset All Settings...

PUSHBUTTON 9940 at 8,66 100×14 DLU, lang 9960 "Reset All Settings..."; the question is a
`WinMessageBox` Yes / No with the question icon, lang 9961 "Reset all 7-Zip settings to their
defaults? 7-Zip will restart." Acts at once (not on Apply). `Support/SettingsReset.swift`:

1. empties the active domain (`com.yrambler2001.7zip`, or `SEVENZIP_DEFAULTS_SUITE`), which holds
   every setting: Options pages, window / panel state, column layouts, histories, favorites,
   compression / extraction options, theme, update-check state, and anything AppKit wrote there;
2. removes `~/Library/Saved Application State/<id>.savedState` (own domain only, never a suite);
3. suspends every write in the process: `NMacPrefs::SetWritesSuspended` (MacPrefs.cpp `SetValue` /
   `Sync`) and `SZSettings.writesSuspended` (also the untyped setter), so `applicationWillTerminate`'s
   `saveAllForTermination` and anything else cannot put state back;
4. starts `/bin/sh -c 'wait for <pid> (30 s max); exec /usr/bin/open -n -a <bundle> [--env ...]'`,
   passing on `SEVENZIP_DEFAULTS_SUITE`, `SZ_TEST_SUPPORT`, `SZ_STATE_DIR`, `SZ_DISABLE_ANIMATIONS`,
   then `NSApp.terminate`.

**Kept, by decision:** `FM.FirstLaunchIntegration` -- without it the next launch of an installed copy
would re-elect the Finder extension and both Quick Actions, re-enabling what the user switched off;
`FM.LaunchServicesStamp*` (only records a registration). Not touched: files, archives, PlugInKit
state, the 7zO*/7zE* temp folders (swept at the next launch as usual).

**Tests.** `Fix112Tests.testResetDecision` (kept keys, helper command line and quoting, saved-state
path); `testResetAllSettingsFromTheMacPage` (No changes nothing; Yes: the domain file holds only the
preserved keys, relaunch scheduled for this bundle with the suite, terminate called; then window
saves, setters, `setPropertyListValue`, the engine's work-dir save and synchronize leave the file
unchanged). `Fix112UITests.testResetAllSettingsEmptiesTheDomainAndRestarts` (real clicks: Tools ▸
Options ▸ macOS ▸ Reset ▸ Yes; the app quits, a new instance of the bundle starts, the seed file
keeps only the marker). Measured on the way: in a process whose domain is a plist **path**,
CFPreferences still answers a removed key with the value the file had when first loaded (the
host's seeded `Lang`, `FM.Panels.numPanels`); the file is right, so the tests read the file.

## 3. Light by default

`FM.Theme` absent or unknown = Light; every choice is stored, System as `"system"`. Through 1.1.1
System was the default and stored as no key, so an explicit System cannot be told apart from never
chosen: both get Light (in the CHANGELOG). `ThemeTests` updated, `Fix112Tests.testLightIsTheDefaultTheme`.

## 4. Homebrew: the cask removes the quarantine flag (tap branch `quarantine`)

The user's decision. Homebrew 7.0.8 deprecates a `postflight` block (`odeprecated`, and `brew style`
fails it with Cask/InstallSteps), so the cask uses the declarative equivalent:

```ruby
postflight_steps do
  run "/usr/bin/xattr",
      args:           ["-dr", "com.apple.quarantine", "{{appdir}}/7-Zip.app"],
      writable_paths: "{{appdir}}/7-Zip.app"
end
```

`writable_paths` is needed: the steps run in Homebrew's cask sandbox. Verified in a throwaway tap
with a renamed cask into a scratch `--appdir`: install of 1.1.0 → no quarantine; upgrade to 1.1.1 →
no quarantine; the same cask without the step → `com.apple.quarantine` present. `brew style` clean,
`brew audit --cask --strict` and `--online` clean. Caveats and tap README state it plainly;
`update-cask.sh` rewrites only `version` / `sha256` (checked on a copy), so releases keep the step.
Main README, release notes and `docs/releasing.md` updated: Homebrew needs no Open Anyway, the DMG
still does.
